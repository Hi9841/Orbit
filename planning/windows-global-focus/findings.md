- `HKCU\Control Panel\Desktop`: `ForegroundLockTimeout=200000`, `ForegroundFlashCount=7`. No explicit `ActiveWindowTracking`, `AutoRaise`, or `ActiveWndTrkTimeout` value appeared in the initial registry read.
- Microsoft documents `SetForegroundWindow` foreground restrictions and taskbar flashing: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow . Microsoft documents that an ALT press or clicking a background window unlocks a foreground lock: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-locksetforegroundwindow . Neither source makes a zero timeout a standard fix for user-initiated taskbar clicks.
- A prior focused probe showed Orbit's visible overlay blocked clicks until `WS_EX_TRANSPARENT` was restored, but this does not explain taskbar failures when Orbit's overlays are hidden. The global task requires fresh evidence.
- The live `SPI_GETFOREGROUNDLOCKTIMEOUT` value is 2,147,483,647 ms despite the saved 200,000 ms value. OpenText documents the same Windows 11 post-logon mismatch in a ZENworks launch issue: https://community.opentext.com/portfolio/zenworks-suite/w/tips/51391/zenworks-understanding-and-resolving-zapp-focus-issues-with-windows-11---part-2 . Clean taskbar clicks succeeded at this live value, so it is not established as this taskbar issue's cause.
